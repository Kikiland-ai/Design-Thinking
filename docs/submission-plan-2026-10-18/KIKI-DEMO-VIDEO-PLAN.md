## How to make the lab sequence convincing

### Record one real run, then edit it

Record the longer experiment first, including the relevant setup, action recognition, baseline run, phase-fault run, restoration and saved notes. Keep the raw take and a short edit log. A 3-minute video does not need to show every click, but each shown result must come from the action and session it claims to follow.

Do not fabricate an all-passed account, set checkpoint state directly in a database, hide a sample banner, or assemble an apparent live sequence from incompatible sessions. An already prepared model is fine when labelled, but it does not prove the student built it under guidance. The strongest edit uses one actual session and a clear “Later in the same lab” caption.

### Choose snippet 08 after a rehearsal

Recommended action: **CP-DSB-03, configure the correctly named Message or Carrier source**, because the setting and target are easy to read. Alternative: a simple named-block placement or connection if it reliably produces a visible guide change on the deployed release.

For the settings example:

1. Start with KiKi's real current action asking for that block's setting.
2. Show the correct block/dialog name and all fields needed by the authored action.
3. The student enters the values and applies them. Keep the dialog visible while it is read.
4. Wait for enough admitted observations and the final committed guidance. A tentative stream preview does not prove a completed action.
5. Show the updated Now and Next in the same take, then close the dialog if instructed.

The tracker generally needs two matching observations from distinct frames. Historical latency has a tail, so 25 seconds may not fit every take. Rehearse on the actual deployment. If a legitimate action takes longer, use the 3:30 cut or reduce other scenes. Do not replace a delayed genuine update with a faster unrelated recording.

**Optional stronger evidence for the 3:30 cut:** retain one actual wrong visible value and its mismatch result, correct it, then show accepted evidence and the new guide action. If the screen is unclear, show KiKi retaining uncertainty instead of claiming a match. Only show status/evidence actually exposed by the current application; do not add a fabricated assessment badge in the edit.

The original backend trial used a separate reader. The final demo should start sharing in **the main application's Lab mode**, then display the windows on MATLAB. If the integrated path does not work, earlier standalone evidence can be shown only with a visible qualification; it does not establish that the submitted app has completed the integration.

### Keep the scientific example consistent

- Message source: amplitude 1, frequency `2*pi*100` rad/s, phase 0.
- Carrier: amplitude 1, frequency `2*pi*2000`, phase `pi/2`.
- **Local carrier is a separate receiver source**, also initially `2*pi*2000` and `pi/2`. Matching numbers in the original Carrier dialog do not prove the Local carrier is configured.
- Baseline receiver: the authored lowpass filter and recovery gain 2. Use the repository's exact procedure, not newly invented filter coefficients.
- Fault: change **only Local carrier phase from `pi/2` to `pi`**. This introduces 90° relative phase error.
- Restore: return Local carrier phase to `pi/2`, then run and compare.

The lesson scene uses **relative phase error**. The simulator block dialog shows **absolute phase in radians**. Make this distinction clear in a small caption if values are visible. At 90° relative mismatch the ideal recovery tends to zero, but the finite-filter simulation may retain residuals. Say “recovery weakens” rather than promise a perfectly flat zero trace.

The authored lab also asks for predictions, observations and explanations. These are useful learning records. Their presence alone does not establish expert-reviewed practical proficiency.

## Screens and footage to prepare before recording

### Recording session

- Use a dedicated real demo account and a fresh product entry. Hide unrelated personal details and notifications. Do not show secrets or service configuration values.
- Use the production app, supported desktop Chrome, release extension with the production origin allowed, real backend/provider configuration and an actual MATLAB Online session with Simulink access.
- Choose one coherent concept: C-AM-08 for carrier alignment, with C-AM-04 as a fallback diagram if media publication is not ready. Label any jump between concepts.
- Prepare a genuine quiz draft so the last answer and submission fit the edit. The account owner should answer it. Keep the actual result even if it is imperfect.
- Save a real short prediction, for example: “If the local carrier phase changes, the recovered message should become weaker.” Use it as student-entered demo content, not a claim that a recruited learner said it.
- Complete the necessary lab actions honestly to reach the relevant checkpoint. Save the external `.slx` model in MathWorks separately.
- For observation, use what the run actually shows. Example only if supported by the output: “Recovery became much weaker with the phase mismatch and returned after restoring the local carrier.”

### Capture quality

- Record at 1920×1080, 30 fps, with an external microphone if available. Keep browser zoom consistent and technical labels readable. Do not sacrifice important parameter fields just to hide chrome.
- Put floating windows where they do not cover the relevant block/dialog or waveform. Their capture masking is a product feature; the visible recording should still show the windows to the viewer.
- Move the cursor deliberately, stop while reading and avoid ornamental zooms. Use hard cuts or short dissolves only where they clarify navigation/time.
- Include accurate subtitles, with readable English explanations when Odia audio plays. Have a native Odia speaker review any translation of that sample.
- Pause voiceover during the actual narration clip. Keep music absent or very low. A team member's conversational voice fits the product story well.

### Evidence during editing

- Preserve at least one uninterrupted action-to-guide update at normal speed.
- Use “Earlier answers completed,” “Later in the same lab” or “Wait shortened” where relevant. Do not speed up model response while leaving an impression of real-time latency.
- Use actual screenshots of result and saved state. A mocked overlay, static prototype or authored animation cannot substitute for working functionality.
- Do not show a console API response as the main proof of the student feature. Use a small backend/service insert only at the technology close.
- Cross-device resume is optional. Showing saved notes after reload is enough for this cut. If changing devices, record actual physical-device continuation on the hosted app. A new device needs its own screen-share consent; live capture does not silently transfer.

## What to leave out of the main video

- Long Google OAuth/onboarding screens. Show the entry, then an honest cut to the returning account.
- Upload processing, Library history and the entire course map tour. They are supporting features and would dilute the lesson-to-lab proof.
- All five dial modes and every glossary word. One meaningful change establishes the interaction.
- Completing all five quiz questions in real time, or the full ten-question chapter test.
- Every one of the forty lab actions. Show one complete evidence loop, then actual later scientific outcomes.
- A separate text/audio generation console, failure/retry API tour or comparison of model names.
- Planned handwriting grading, viva, hardware verification, teacher dashboards or autonomous cursor actions.
- Claims about marks, fluency or learning improvements without a study.

## If a feature misses the recording deadline

If showing the older standalone backend trial, label it prominently as a separate prototype and describe the integrated app's actual limits in the deck. That honest fallback is weaker evidence and does not cure a non-working mandatory deployed prototype.

**No public deployed prototype:** the video is not a replacement for that submission requirement. Resolve the deployment/access issue before declaring the package ready.
